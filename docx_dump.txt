Résumé
Ce projet de fin de matière, intitulé SentimentAI Morocco, porte sur la conception et le développement d'un système intelligent de suivi en temps réel de l'opinion publique et des tendances numériques au Maroc. La solution repose sur une architecture Big Data complète, intégrant un pipeline de collecte automatisé, un moteur d'analyse de sentiment multiculturel et un tableau de bord interactif haute performance.
La collecte de données est assurée par un parseur RSS développé en Python, exploitant le flux XML de r/Morocco/new.rss via xml.etree.ElementTree afin de contourner les limitations de l’API JSON officielle de Reddit (blocages HTTP 403). Ces données brutes sont ensuite traitées par un pipeline MapReduce distribué sur un cluster Apache Hadoop déployé sous Docker Compose, articulé en cinq jobs séquentiels exécutés via l’API Hadoop Streaming : nettoyage et normalisation des données, scoring NLP par un modèle de machine learning scikit-learn (TF-IDF + Régression Logistique), détection des hashtags dominants par pondération TF-IDF, détection d’anomalies temporelles, et calcul de la vélocité de tendance géo-temporelle — contribution algorithmique originale du projet.
Un tableau de bord interactif a été développé en HTML/CSS/JavaScript vanilla, animé par GSAP et alimenté par une API FastAPI. Il intègre une carte choroplèthe du Maroc (Leaflet.js), un fil de publications en temps réel, un graphique de vélocité de sentiment (Chart.js), un visualiseur de pipeline MapReduce animé et un panneau d'alertes avec classement dynamique. L'ensemble du système fonctionne avec des données réelles ou simulées, et est facilement commutable entre les deux modes.
Ce projet illustre l'importance des technologies Big Data et de l'intelligence artificielle dans la transformation de flux de données non structurées en outils stratégiques d'aide à la décision et de veille numérique, au service de la transformation digitale du Maroc.
Mots-clés : Big Data, Apache Hadoop, Hadoop Streaming, Analyse de sentiment, NLP, scikit-learn, FastAPI, GSAP, Leaflet.js, Python, Temps réel, Maroc.
Abstract
This end-of-course project, titled SentimentAI Morocco, focuses on the design and development of an intelligent system for real-time monitoring of public opinion and digital trends in Morocco. The solution is built on a comprehensive Big Data architecture, integrating an automated data collection pipeline, a multicultural sentiment analysis engine, and a high-performance interactive dashboard.
Data collection is handled by a Python RSS feed parser leveraging the r/Morocco/new.rss XML endpoint via xml.etree.ElementTree, bypassing the HTTP 403 rate-limiting blocks imposed by Reddit’s official JSON API. These raw data are then processed by a distributed MapReduce pipeline running on an Apache Hadoop cluster deployed via Docker Compose, structured around five sequential jobs executed through the Hadoop Streaming API: data cleaning and normalisation, NLP sentiment scoring using a pre-trained scikit-learn model (TF-IDF vectoriser and Logistic Regression classifier), dominant hashtag detection via TF-IDF weighting, temporal anomaly detection, and geo-temporal trend velocity computation — an original algorithmic contribution of the project.
An interactive dashboard was developed in vanilla HTML/CSS/JavaScript, animated by GSAP and powered by a FastAPI backend. It features a Morocco choropleth map (Leaflet.js), a real-time post feed, a sentiment velocity chart (Chart.js), an animated MapReduce pipeline visualiser, and a dynamic alert panel with live ranking. The system operates with real or simulated data and can be seamlessly switched between the two modes.
This project demonstrates the importance of Big Data technologies and artificial intelligence in transforming unstructured data streams into strategic decision-support and digital intelligence tools, in service of Morocco's digital transformation.
Keywords: Big Data, Apache Hadoop, Hadoop Streaming, Sentiment Analysis, NLP, scikit-learn, FastAPI, GSAP, Leaflet.js, Python, Real-time, Morocco.

Introduction générale
À l'ère du numérique, les réseaux sociaux génèrent chaque seconde des millions de publications reflétant les opinions, les émotions et les préoccupations d'une société. Cette explosion de données non structurées représente un défi technologique majeur, mais également une opportunité sans précédent pour les acteurs économiques, politiques et académiques qui souhaitent comprendre et anticiper les dynamiques de l'opinion publique.
C'est dans ce contexte que s'inscrit SentimentAI Morocco, un projet ambitieux visant à concevoir et développer une plateforme Big Data intelligente dédiée au suivi en temps réel du climat numérique au Maroc. En exploitant les données massives issues de Reddit, le système analyse automatiquement le sentiment exprimé par les internautes marocains, détecte les tendances émergentes et alerte sur les anomalies de manière proactive.
La pertinence de ce projet est renforcée par le contexte marocain spécifique : un pays à la croisée des influences culturelles arabes, berbères et françaises, où les interactions numériques mêlent dialecte darija, arabe classique et français. Cette réalité linguistique impose des défis particuliers en matière de traitement du langage naturel, que notre solution aborde par l’intégration d’un modèle scikit-learn pré-entraîné (TfidfVectorizer + Régression Logistique) directement dans le Mapper Hadoop, en conservant le lexique AFINN-111 enrichi de termes marocains comme mécanisme de repli déterministe.
Sur le plan technique, le projet mobilise un ensemble cohérent de technologies Big Data modernes : Apache Hadoop via Docker Compose pour le traitement véritablement distribué à grande échelle, l’API Hadoop Streaming pour l’exécution des scripts Python mapper.py et reducer.py au sein de l’écosystème HDFS, FastAPI pour l’orchestration et l’exposition des données, et un tableau de bord HTML/JavaScript animé par GSAP pour la visualisation temps réel. L’originalité algorithmique du projet réside dans le Job 5 du pipeline MapReduce, qui introduit le concept de vélocité de tendance géo-temporelle : plutôt que de simplement mesurer le sentiment actuel, le système calcule sa vitesse de changement par région et par semaine, permettant ainsi la détection précoce des crises avant qu’elles n’atteignent leur pic.
Ce rapport est structuré en quatre chapitres complémentaires. Le premier chapitre présente le contexte général du projet, les technologies mobilisées et la problématique adressée. Le deuxième chapitre détaille l'analyse des besoins fonctionnels et non fonctionnels ainsi que l'architecture décisionnelle conçue. Le troisième chapitre décrit l'implémentation technique de 
chaque composant du système. Le quatrième chapitre présente et analyse les résultats obtenus, avant de conclure sur les apports et les perspectives du projet.

1. Big Data et Analyse de Sentiment : Fondements Théoriques
1.1 Le paradigme Big Data
Le Big Data désigne l'ensemble des technologies et méthodologies permettant de collecter, stocker, traiter et analyser des volumes de données massifs, dépassant les capacités des systèmes de traitement traditionnels. Il se caractérise par les cinq dimensions du modèle des 5V :
Volume : 
des téraoctets, voire des pétaoctets de données générées en continu.
Vélocité : 
des flux de données produits et consommés en temps quasi-réel.
Variété : 
des formats hétérogènes (texte, image, audio, JSON, CSV...).
Véracité : 
la nécessité de filtrer les données bruit et incomplètes.
Valeur : 
la transformation des données brutes en insights stratégiques actionnables.
Le paradigme MapReduce, introduit par Google (Dean & Ghemawat, 2008), décompose tout traitement en deux phases : une phase Map qui filtre et transforme les données en paires clé-valeur, et une phase Reduce qui agrège les résultats. Dans notre implémentation, la phase Map est distribuée sur un cluster Apache Hadoop (1 NameNode, 1 ResourceManager, 1 HistoryServer, 4 DataNodes) via l’API Hadoop Streaming, qui exécute directement les scripts Python mapper.py et reducer.py au sein de l’écosystème HDFS. Le NameNode orchestre la distribution des fichiers .jsonl bruts vers les DataNodes, où les Mappers s’exécutent en parallèle et écrivent les paires clé-valeur (Région → Score de sentiment) en HDFS. Cette architecture garantit la tolérance aux pannes, la réplication des données et une scalabilité horizontale réelle.
1.2 L'analyse de sentiment et le Traitement du Langage Naturel
L'analyse de sentiment (ou opinion mining) est un domaine de la linguistique computationnelle visant à identifier automatiquement l'opinion exprimée dans un texte : positive, négative ou neutre. Elle mobilise des techniques de Traitement du Langage Naturel (NLP) parmi lesquelles :
Approches lexicales : 
utilisation de dictionnaires de sentiment (AFINN, SentiWordNet, VADER) qui associent un score numérique à chaque terme.
Approches par apprentissage machine : 
classification supervisée (Naive Bayes, SVM, BERT) entraînée sur des corpus annotés.
Approches hybrides : 
combinaison des deux pour améliorer la robustesse sur des textes dialectaux ou multilingues.
Le contexte marocain présente des défis linguistiques spécifiques : la darija (dialecte arabe marocain), l’arabe classique et le français coexistent dans les publications sociales, souvent au sein d’un même message (code-switching). Notre solution adopte une approche hybride à deux niveaux : un modèle de machine learning pré-entraîné (TfidfVectorizer + Régression Logistique, fichier Model final.joblib) constitue le moteur d’inférence principal, tandis que le dictionnaire AFINN-111 enrichi de termes marocains intervient exclusivement comme mécanisme de repli déterministe en cas de défaillance du modèle ML.
2. Contexte du Projet
SentimentAI Morocco s'inscrit dans le cadre du module Big Data et Traitement Distribué de la filière Ingénierie Informatique et Réseaux (IASDT) de l'EMSI Tanger. Le projet répond à une problématique réelle et d'actualité : la nécessité pour les acteurs marocains (entreprises, institutions, médias) de disposer d'outils de veille numérique capables d'analyser en temps réel le sentiment exprimé sur les réseaux sociaux par rapport aux événements nationaux.
La montée en puissance des réseaux sociaux au Maroc est significative : avec plus de 22 millions d'utilisateurs d'internet et un taux de pénétration des réseaux sociaux dépassant 50% de la population, Reddit constituent des baromètres précieux du climat d'opinion, notamment lors d'événements sportifs (CAN 2025, Coupe du Monde 2030), politiques ou économiques majeurs.
3. Problématique
Comment exploiter des données massives et hétérogènes issues des réseaux sociaux
pour identifier en temps réel les corrélations entre régions géographiques,
périodes temporelles et évolution du sentiment public marocain,
et produire un système d'alerte précoce sur les tendances émergentes ?
Cette problématique soulève plusieurs défis techniques interdépendants :
Comment collecter en continu des données massives depuis plusieurs API sociales sans interruption de service ?
Comment analyser le sentiment dans un contexte multilingue et dialectal (darija, arabe, français) avec une précision satisfaisante ?
Comment détecter les tendances non pas par leur valeur absolue, mais par leur vitesse de changement, pour anticiper les crises ?
Comment visualiser ces informations de manière fluide, intuitive et temps réel, adaptée aux besoins d'analyse stratégique ?
4. Objectifs du Projet
4.1 Objectifs fonctionnels
Collecter automatiquement des publications sociales depuis Reddit ciblant les 8 régions du Maroc.
Analyser le sentiment de chaque publication (score entre -1 et +1) en tenant compte du multilinguisme marocain.
Détecter les hashtags dominants par région et par période en éliminant les tags globalement viraux.
Identifier les anomalies temporelles : régions dont l'activité dépasse de 50% la moyenne des 6 semaines précédentes.
Calculer la vélocité de tendance géo-temporelle et produire un classement des régions par urgence d'alerte.
Visualiser l'ensemble de ces informations sur un tableau de bord interactif et animé en temps réel.
4.2 Objectifs techniques
Déployer un cluster Apache Hadoop distribué (1 NameNode + 4 DataNodes) via Docker Compose et exécuter un pipeline MapReduce en 5 jobs séquentiels via l’API Hadoop Streaming (mapper.py et reducer.py).
Développer un backend Python FastAPI servant de couche API entre le pipeline et le tableau de bord.
Créer un tableau de bord HTML/CSS/JavaScript vanilla avec des animations GSAP de qualité professionnelle.
Garantir une architecture modulaire permettant le passage transparent entre données simulées et données réelles.
Documenter l'ensemble du système (docstrings Python, JSDoc, README) pour faciliter la maintenance.

2.2 Flux de données
Le flux de données traverse le système de manière unidirectionnelle, du scraper jusqu'au tableau de bord, selon la séquence suivante :
Le scraper.py collecte les publications toutes les 60 secondes via le parseur RSS (r/Morocco/new.rss) et les écrit en /data/raw/YYYY-MM-DD.jsonl.
Le sentiment_processor.py est déclenché immédiatement après chaque cycle de scraping. Il score les publications non encore traitées et produit les fichiers JSON dans /data/processed/.
FastAPI lit ces fichiers JSON et les expose via 6 endpoints REST avec en-tête Cache-Control: no-store.
Le DataPoller JavaScript interroge les 6 endpoints toutes les 5 secondes via Promise.all() et émet des CustomEvents pour chaque panneau du tableau de bord.
Chaque module de panneau écoute son événement et met à jour son affichage avec des animations GSAP.

Les fichiers .jsonl bruts sont d’abord transférés en HDFS, puis le NameNode orchestre leur distribution vers les DataNodes qui exécutent les Mappers en parallèle. 3. Conception Détaillée des Composants Clés
3.1 Le module d'inférence géographique
L'inférence de la région géographique d'une publication est assurée par region_inferrer.py, un module léger sans dépendance externe. Il utilise un dictionnaire de mots-clés associant chaque région marocaine à ses villes, quartiers et références culturelles principales. La fonction infer_region(text) retourne le nom de la région si au moins un mot-clé est trouvé dans le texte (insensible à la casse), ou None si aucune correspondance n'est détectée.
Les 8 régions couvertes sont : Tanger-Tétouan-Al Hoceïma, Casablanca-Settat, Rabat-Salé-Kénitra, Fès-Meknès, Marrakech-Safi, Souss-Massa, Oriental, et Drâa-Tafilalet.
3.2 Le Job 5 — Vélocité de tendance géo-temporelle (contribution originale)
Le Job 5 constitue la contribution algorithmique originale de ce projet. Contrairement à une mesure statique du sentiment, il calcule la vitesse de changement du sentiment par région et par semaine, selon la formule :
v(r,t) = ( S(r,t) − S(r,t−7) ) / 7
où S(r,t) est le score moyen de sentiment pour la région r à la semaine t
L'implémentation Python repose sur le tri secondaire (Secondary Sort) : une clé composite RegionWeekKey garantit que la fonction Reduce reçoit les enregistrements dans l'ordre chronologique strict, sans tri en mémoire. Un partitionneur personnalisé partitionne par région uniquement, un GroupingComparator groupe par région, et un SortComparator trie par région puis par semaine croissante. Cela permet le calcul d'une fenêtre glissante de 7 jours directement dans la phase Reduce, avec une complexité O(n) au lieu de O(n log n).

Chapitre 3: 
Implémentation et Développement de la Solution
Introduction
Ce chapitre décrit l’implémentation technique de l’ensemble des composants de SentimentAI Morocco, depuis le pipeline MapReduce distribué sur cluster Apache Hadoop jusqu’au tableau de bord animé, en passant par le backend Python FastAPI. Chaque composant est présenté dans son contexte fonctionnel, avec les choix d’implémentation justifiés.
1. Pipeline MapReduce — Architecture Hadoop Distribué
1.1 Structure du projet Python
Le cluster Apache Hadoop est déployé via Docker Compose et comprend les services suivants : un NameNode (maître HDFS et gestionnaire des métadonnées), un ResourceManager (gestionnaire des ressources YARN), un HistoryServer (historique des jobs), et 4 DataNodes (nœuds de stockage et d’exécution). L’API Hadoop Streaming est utilisée pour soumettre les jobs : elle permet d’exécuter directement les scripts Python mapper.py et reducer.py sans réécriture en Java, en lisant depuis stdin et écrivant vers stdout selon le protocole MapReduce. Les fichiers .jsonl bruts sont transférés en HDFS avant chaque exécution via les commandes hdfs dfs, et les résultats de chaque job sont récupérés en local avant d’être passés au job suivant par le driver driver.py.
1.2 Job 1 — Nettoyage et normalisation
Le script mapper.py du Job 1 lit chaque ligne JSON brute depuis stdin (alimenté par HDFS via Hadoop Streaming), valide la structure (post_id, date, text, source), filtre les lignes incomplètes, normalise le texte (minuscules, suppression des URLs et mentions), détecte la langue par détection de trigrams, et émet vers stdout la paire clé-valeur tabulée : région\ttoken|date|langue|source. Le script reducer.py correspondant déduplique les enregistrements identiques et produit un corpus nettoyé stocké en HDFS au format JSONL. Le NameNode orchestre la distribution des blocs de données entre les 4 DataNodes, où les instances du Mapper s’exécutent en parallèle, assurant une véritable distribution des calculs.
Le mapper.py charge la liste de stopwords au démarrage depuis un fichier de ressources local. Les blocs HDFS répartis sur les 4 DataNodes sont traités en parallèle par autant d’instances du Mapper, ce qui confère au Job 1 une scalabilité horizontale naturelle sans aucune modification du code.
1.3 Job 2 — Scoring NLP par lexique
Le mapper.py du Job 2 constitue le cœur du pipeline d’apprentissage automatique. À son initialisation, il charge le modèle pré-entraîné scikit-learn (fichier Model final.joblib) via joblib.load(). Ce modèle encapsule une pipeline composée d’un TfidfVectorizer et d’un classificateur de Régression Logistique entraîné sur un corpus annoté. Pour chaque publication reçue depuis stdin, le mapper applique le modèle et obtient une distribution de probabilités sur trois classes : P_pos (probabilité positive), P_neu (probabilité neutre) et P_neg (probabilité négative). Le score continu est calculé selon la formule Score = P_pos − P_neg, ce qui projette le résultat sur l’échelle [-1.0, +1.0] de la carte heatmap : les déclarations neutres (P_neu élevé) sont écrasées à zéro tandis que la confiance négative est pénalisée. La classification émotionnelle complexe est déterminée par une logique de seuil : si P_pos > 0,45, le post est étiqueté « Pride/Joy » ; si P_neg > 0,45, il reçoit l’étiquette « Grievance ». En cas de défaillance du modèle ML (exception à l’inférence), le mapper bascule automatiquement sur le dictionnaire AFINN-111 enrichi (2 400 mots + 50 termes en dialecte marocain) comme mécanisme de repli déterministe. La paire clé-valeur émise vers stdout est : région|semaine\tscore|émotion.
Le reducer.py du Job 2 agrège les scores par (région, semaine) et produit un vecteur de sentiment comprenant : score moyen, écart-type, distribution de polarité (positif %, neutre %, négatif %), émotion dominante et nombre de posts. Cette sortie est écrite en HDFS et récupérée par le driver pour alimenter le Job 4 (détection d’anomalies) et le Job 5 (vélocité).
1.4 Job 3 — Détection des hashtags dominants par TF-IDF
Le Mapper extrait tous les hashtags (#tag) de chaque post par expression régulière et émet (hashtag|région|semaine, 1). Le Reducer compte les occurrences et applique une pondération TF-IDF adaptée aux séries temporelles : le score TF-IDF d'un hashtag dans une région est son compte local divisé par son compte global sur l'ensemble des régions (log-normalisé). Cela pénalise les hashtags globalement viraux (#Maroc, #Botola) et fait remonter les tendances réellement locales. Le Top-N est sélectionné par région via une PriorityQueue bornée dans le Reducer.
1.5 Job 4 — Détection d'anomalies temporelles
Le Mapper émet (région|semaine, nb_posts) avec une clé composite et un tri secondaire sur l'horodatage. Le Reducer compare le compte de la semaine courante à la moyenne des 6 semaines précédentes. La condition d'alerte est : nb_posts_actuel > moyenne_6_semaines × 1,5. En cas d'alerte, le Reducer émet (région|semaine, score|ALERTE=OUI|spike_pct). Cette logique de fenêtre glissante est rendue efficace par le tri secondaire, qui garantit l'ordre chronologique des enregistrements dans le Reducer.
1.6 Job 5 ★ — Vélocité de tendance géo-temporelle
C'est le composant le plus innovant du pipeline. La classe RegionWeekKey implémente WritableComparable avec deux champs : region (Text) et week (IntWritable). Le RegionWeekPartitioner partitionne exclusivement sur le hash de la région, le RegionWeekGroupComparator groupe par région uniquement, et le RegionWeekSortComparator trie par (région ASC, semaine ASC). Cette configuration garantit que le Reducer reçoit tous les scores d'une région dans l'ordre chronologique, sans aucun tri en mémoire.
Le VelocityReducer implémente une fenêtre glissante de 7 jours : il maintient une liste des scores des 7 dernières semaines et calcule v(r,t) = (S(r,t) − S(r,t−7)) / 7 pour chaque nouvelle semaine reçue. La sortie est une matrice région × semaine → vélocité, triée par vélocité absolue décroissante pour produire un classement des régions par urgence d'alerte.
2. Backend Python — FastAPI
2.1 Structure et organisation
Le backend est organisé en 4 modules Python indépendants et un fichier de configuration YAML. L'ordre d'importation respecte les dépendances : region_inferrer.py (aucune dépendance), sentiment_processor.py (dépend de region_inferrer), scraper.py (dépend des deux précédents), main.py (orchestre l'ensemble via FastAPI).
2.2 Scraper et gestion des APIs sociales
Le scraper.py utilise APScheduler pour déclencher le cycle de collecte toutes les 60 secondes comme un événement FastAPI lifespan. L’API JSON officielle de Reddit ayant été abandonnée en raison de blocages systématiques HTTP 403 Forbidden liés au rate limiting, la collecte repose désormais sur un parseur de flux RSS XML. Le module xml.etree.ElementTree analyse le flux r/Morocco/new.rss, extrait les balises <title>, <link> et <description> de chaque entrée, et constitue un objet publication structuré. Cette approche contourne efficacement les protections anti-scraping de Reddit tout en garantissant l’authenticité des discussions communautaires collectées en temps réel. Les publications sont ensuite enrichies par le module region_inferrer.py (inférence géographique) avant d’être sérialisées en JSONL atomique : chaque fichier est d’abord écrit sous un nom temporaire (fichier.tmp) puis renommé via os.replace(), évitant qu’un polling API ne lise un fichier à moitié écrit.
Toutes les écritures sur disque sont atomiques : le fichier est écrit dans un nom temporaire (fichier.tmp) puis renommé via os.replace(), évitant ainsi qu'un polling API ne lise un fichier JSON à moitié écrit.
2.3 Endpoints REST
FastAPI expose 7 endpoints avec CORS activé pour toutes les origines et en-tête Cache-Control: no-store sur toutes les réponses :
GET / → sert index.html depuis le répertoire dashboard/.
GET /api/feed → derniers 100 posts scorés, triés par date décroissante.
GET /api/heatmap → score moyen par région (snapshot courant).
GET /api/velocity → matrice région × semaines → vélocités (8 semaines).
GET /api/alerts → alertes actives avec région, sujet, spike%, timestamp, sévérité.
GET /api/pipeline → statut des 5 jobs MapReduce (pending|running|done|error).
POST /api/scrape/now → déclenche un cycle de scraping immédiat (BackgroundTask).
POST /api/test-nlp → reçoit un texte libre (français ou darija), l’insère dans le pipeline ML (TF-IDF + Logistic Regression), et retourne instantanément le score continu [-1.0, +1.0] et l’étiquette émotionnelle assignée. Cet endpoint alimente le modal interactif « Test NLP » du tableau de bord.
Tous les endpoints retournent une structure vide valide ([], {}) si les fichiers JSON n’existent pas encore, évitant tout code 500 lors du premier démarrage. L’endpoint /api/test-nlp accepte un corps JSON {“text”: “...”} et applique directement le modèle Model final.joblib, permettant aux utilisateurs de tester interactivement le classifieur sans déclencher un cycle de scraping complet.
3. Tableau de Bord — Frontend JavaScript
3.1 Architecture événementielle
Le tableau de bord est architecturé selon un pattern événementiel strict : DataPoller est l'unique source de données. Il interroge les 6 endpoints toutes les 5 secondes via Promise.all() et émet des CustomEvents (data:feed, data:heatmap, data:velocity, data:alerts, data:pipeline, data:hashtags). Chaque module de panneau écoute son propre événement et ne contient aucun appel fetch(). Cette architecture garantit un couplage nul entre les panneaux et facilite le basculement entre mode simulation et mode données réelles.
3.2 Pipeline Visualiseur (Panel 1)
Le panneau supérieur affiche les 5 jobs MapReduce sous forme de nœuds connectés par des lignes animées. Des points lumineux voyagent le long des connecteurs via des timelines GSAP repeat:-1 avec ease:'none' pour simuler le flux de données en temps réel. Chaque changement de statut de job déclenche une animation spécifique : pulse CSS pour running, popComplete() avec easing élastique pour done, shakeElement() pour error. Un drawer de détail slide-in s'affiche au clic sur chaque nœud.
3.3 Carte choroplèthe Maroc (Panel 2)
La carte Leaflet.js utilise un GeoJSON des régions marocaines embarqué directement dans heatmap.js (const MOROCCO_GEOJSON), sans aucune requête externe, garantissant l'affichage en conditions de réseau limité. L'échelle de couleurs utilise gsap.utils.mapRange() pour interpoler les scores [-1, +1] vers une gamme de couleurs rouge → gris → vert (#A32D2D → #444441 → #0F6E56). Les transitions de couleur sont animées via CSS transition: fill 0.6s ease appliqué aux paths SVG de Leaflet. Les régions en alerte affichent un contour animé par CSS @keyframes stroke-dashoffset.
3.4 Animations GSAP et performance
Toutes les animations respectent les principes de performance GSAP : seules les propriétés transform et opacity sont animées (aucune animation de propriétés layout comme width, height, top, left). Les éléments animés fréquemment (points du pipeline, cartes du fil d'actualités, cartes de classement) bénéficient de will-change: transform. La timeline de chargement initial utilise le paramètre position de gsap.timeline() pour superposer les animations et réduire la durée totale d'entrée à 2 secondes. Un wrapper gsap.matchMedia() désactive les animations non essentielles si prefers-reduced-motion est actif.
3.5 Le classement dynamique (Flip pattern)
Le panneau des alertes affiche un Top 5 des régions classées par vélocité absolue. Lorsque l'ordre change entre deux polls, le re-classement est animé via le Flip pattern manuel : avant le réordonnancement DOM, les positions actuelles sont enregistrées via getBoundingClientRect() pour chaque carte. Après réordonnancement, GSAP anime chaque carte depuis son ancienne position vers sa nouvelle position (gsap.from(card, {x: old.x - new.x, 
y: old.y - new.y, duration: 0.6, ease: 'power2.inOut'})). Cela donne l'impression que les cartes glissent physiquement vers leur nouveau rang.
Conclusion
3.6 Interface de Test NLP Interactif
Afin de permettre une validation pédagogique et démonstrative du moteur NLP, une interface de test interactif a été intégrée directement au tableau de bord. Un bouton « Test NLP », visible en permanence dans la barre de navigation, déclenche l’ouverture d’un modal glassmorphique — rendu par un effet de flou d’arrière-plan CSS (backdrop-filter: blur) et une transparence partielle — qui s’affiche au premier plan sans interrompre l’animation du tableau de bord en cours.
L’utilisateur (enseignant, jury, démonstrateur) saisit une phrase libre en français ou en darija dans un champ de texte, puis soumet la requête au nouvel endpoint POST /api/test-nlp. Le backend FastAPI transmet immédiatement le texte au modèle Model final.joblib, qui retourne les probabilités P_pos, P_neu et P_neg, le score continu Score = P_pos − P_neg, et l’étiquette émotionnelle calculée par seuil. Ces résultats sont affichés en temps réel dans le modal, avec une barre de progression colorée représentant visuellement le score sur l’axe [-1.0, +1.0]. Cette fonctionnalité supprime le besoin d’attendre un cycle de scraping complet pour vérifier le comportement du classificateur sur des phrases spécifiques, et constitue un outil pédagogique précieux lors des séances de défense.

2.2 Analyse des résultats NLP

4. Évaluation Critique de la Solution
4.1 Points forts
Innovation algorithmique : 
le Job 5 de vélocité géo-temporelle est une contribution originale, absente des tutoriels MapReduce existants.
Architecture modulaire : 
chaque couche est indépendante et remplaçable sans impact sur les autres.
Robustesse : 
contournement des blocages HTTP 403 Reddit par parseur RSS, tolérance aux pannes Hadoop (réplication HDFS), écriture atomique Python, mode simulation transparent.
Qualité visuelle : 
animations GSAP professionnelles, zéro saut visuel, performance 60fps maintenue.
Portabilité : 
le tableau de bord fonctionne sans serveur local (double-clic index.html) et sans framework JavaScript.
4.2 Limitations et perspectives
Précision NLP : 
le classificateur TF-IDF + Régression Logistique actuel atteint un F1 de 76,1%. Un modèle de deep learning pré-entraîné sur corpus marocain (AraBERT, DarijaBERT) améliorerait significativement la précision sur le dialecte marocain.
Couverture des sources : 
l'intégration de Facebook, Instagram et TikTok (API Meta) élargirait considérablement la base de données.
Scalabilité Hadoop : 
les tests ont été conduits sur un cluster local de 4 DataNodes. Un déploiement sur infrastructure cloud (AWS EMR, GCP Dataproc) permettrait de valider la scalabilité horizontale sur des volumes de données représentatifs d’une production nationale.
Temps réel strict : 
l'architecture actuelle offre une latence de ~65 secondes (60s scraping + 5s polling). Kafka + Spark Streaming permettrait d'atteindre une latence inférieure à 5 secondes.
Conclusion
Ce chapitre a démontré que SentimentAI Morocco atteint ses objectifs fonctionnels et techniques. Le pipeline MapReduce traite efficacement les données, le module NLP atteint un F1 de 76,1% sur corpus multilingue marocain, et le tableau de bord offre une expérience de visualisation fluide et professionnelle. Les perspectives d'évolution identifiées ouvrent la voie à une solution de veille numérique nationale à l'état de l'art.

le déploiement du cluster Hadoop sur infrastructure cloud (AWS EMR, GCP Dataproc) permettrait de valider la scalabilité horizontale à l’échelle nationale, tandis qu’une interface d’administration rendrait la solution accessible à des utilisateurs non-développeurs.
